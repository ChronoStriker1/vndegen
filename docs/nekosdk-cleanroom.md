# NekoSDK runtime: clean-room provenance

VNDegen runs NekoSDK games on its own runtime, `Packages/VNDegenKit/Sources/CNekoSDK`, under VNDegen's MIT license. No
runtime, partial runtime or engine documentation exists for NekoSDK. This file lists where the runtime's knowledge came
from and which meanings are settled. The rule is in `docs/roadmap.md`'s Licenses section: only permissively licensed code,
and nothing copied or ported from GPL, LGPL or unlicensed code.

## Sources

### What the runtime's author used

- **The games' own files.** Test Games 95 and 97, and Test Game 82 during planning: archives, scripts, `init.ini` and the
  other configuration files, pictures and sounds.
- **The PC games under Wine, as black boxes.** Headless gamescope for stills and input, Xvfb with `x11grab` for video, on
  CachyOS. Real saves made there, and recordings of the opening of Test Game 97.
- **The executables, by strings and imports only.** `strings` for the asset names and scene lists, and the import table.
  Test Game 94's `rinjin.exe` was disassembled once, on 2026-11-07, without asking first, for the four behaviours
  [read from Test Game 94's exe](#read-from-test-game-94s-exe) lists. The coordinator approved that use after the fact the
  same day. The Alchemist's `alchemy.exe` was disassembled on 2026-11-08 with approval given in advance, for the film
  noise alone ([the film noise](#the-film-noise-read-from-the-alchemists-exe)). No other executable has been disassembled
  or decompiled. Any disassembly needs the coordinator's approval first.
- **VNDegen's own earlier code.** `audio`, `font` and `sjis` are adapted from the System 4 runtime. `stb_image` and
  `stb_vorbis` (public domain or MIT) are the same copies System 4 uses, and zlib (zlib license) unpacks archives.
- **VNDegen's own feasibility test,** `docs/nekosdk.md` and its Python tools on branch `ws/nekosdk`.

The runtime's author opened none of the outside projects below.

## The script node layout, re-checked

`Engines/NekoSDK/host/tools/nekocheck.cpp` reads every script of a game and requires three things: each file parses to its
exact last byte, each `next` names a node, and the numbers each node shows in its readable first string (`time:`, `type:`,
`ch:`, `vol:`, `pos:`, `tm:`, `loop:`) equal its parameters. That last check is independent of any outside description:
the editor wrote the same value twice, once as text and once as a number, so the layout is right if they agree.

| Game | Scripts | Nodes | Unreadable | Bytes after the last node | `next` naming nothing | Fields compared | Differing |
|---|---|---|---|---|---|---|---|
| Test Game 97 | 7 | 2,446 | 0 | 0 | 0 | 3,056 | 0 |
| Test Game 95 | 93 | 31,494 | 0 | 0 | 0 | 27,537 | 0 |

## Saves

A `.sav` uses the archive entry container: the first 4 bytes XORed with the rolling key the archive uses, a zlib stream, and the unpacked size in the last 4 bytes. This was found by testing the archive's scheme on saves the PC game wrote.

Inside is a stream of fields, mostly zero. `Engines/NekoSDK/host/tools/nekosave.cpp` reads a save and writes it back. Test Game 97's saves come back with at most 4 bytes different in about 140,000, and Test Game 95's with 9 or more. Those bytes are state the runtime doesn't use, on the last sprite record.

| Field | Where | How it was settled |
|---|---|---|
| A first byte of 1, then 204 zeros | Start | All saves |
| Flow script name, u32 length and bytes | 0xCD | Read from the file. An older game with no flow scripts has length 0 |
| 4,196 bytes, a choice picture's name, then 39,596 bytes | | Test Game 95's saves after a choice hold the picture named by its choice command |
| Date and time as six ints, in 400 bytes | | The save screen shows them |
| 1, then the flow node of the scene call | | Test Game 95's node 6 and 12 match the scenes each save resumes |
| 10,000 ints: the scenario's variables | The last 40,000 bytes before the sprite count | `macrolist.ini` names 110 and 4000. A save after a choice that raises the counter holds 1 at 110 |
| Sprite count, then 40 bytes, then records | | The root record has slot -999999 and the window's size |

A sprite record is a slot, two picture paths, then fixed fields: a matrix, x and y, scale, the anchor (the point a scale keeps still, which the section on placing pictures covers), alpha out of 256, whether blur is on and its amount, whether an animation runs, how many frames in, its text, then the sprite's end state. Test Game 95's record has 69 more bytes than Test Game 97's and Test Game 82's first fields agree with the older layout.

After the records come the text on screen and the last 60 lines of the backlog, newest first, then 243 sound channel records (60 of music, then sound effects), each a playing flag, path, volume, pan and position in seconds as a double. Then the scene script's name and the node to run next.

**Checked both ways on Test Game 97 under Wine:** a save the PC wrote loads in the runtime, shows the same text, and moves on to the next line. A save the runtime wrote appears on the PC's load screen with its date and thumbnail, loads, shows the same text, and moves on. Test Game 95's saves load in the runtime. A save the runtime writes for Test Game 95 hasn't been loaded on its PC copy yet.

`cfg.sav` holds the PC's settings, with the 10,000 global variables at byte 4000 (a macro of 1000 sits at byte 8000 after the prologue). The runtime keeps the rest of the file as it found it. `read.sav`, packed the same way, lists the scripts the PC has read to their end: a count, then for each its name's length, the name, a count of node ranges, and the ranges as pairs of ints, the last two (0, 0) and (-2, -2). The runtime reads the names for the Scene gallery (below), and the ranges, inclusive node ids, as text already read for Config's read-only skip, which stops at the first line not read. The marks are every node the PC has run, not only text: Test Game 89's file gives a scene's script `(131, 132), (214, 214), (280, 280)`, a stretch of two lines then a music stop and a clear, consecutive ids along the chain. A script is listed once it has been read to its end. VNDegen keeps its own marks in `vndegen_read.txt` and writes `read.sav` back the same way, the PC's scripts first, in its order and with its ranges and any read since, then each script finished in VNDegen. Checked under Wine: with the file VNDegen wrote, the PC showed the scene finished in VNDegen unlocked, and its read-only skip (Config's byte 28 of `cfg.sav`) ran through the text read in VNDegen and stopped where that reading ended. Config's settings are kept in a small file of VNDegen's, so they don't move to or from a PC.

The same file keeps what's been unlocked, read by comparing PC files with what the PC's galleries show: an int at byte 48000 plus 4 times each picture's number in `cg_view.ini`, and an int for each track in `sound_view.ini` from byte 100000. Both move by the length of a string at byte 44020 that names the last script read to its end (Test Game 89's changed from `ep_001_004_100` to `ep_001_005_000` as that script ended): a file the PC has just made has none and is 104,000 bytes, and one with a 22-character name has its tables 22 bytes later. Test Game 95's file with 5, 4 and 7 pictures seen in its first three entries, and its 10 tracks heard of 15, gives those numbers, and Test Game 97's file agrees on the tracks. A CG row in Test Game 97 is assumed to match.

Test Games 92 and 93's music screens pan line art behind the track list, measured under Wine by tracking each frame against the five 2200-pixel-tall sketches `obj\g000_001` to `_006`. They come in the order 001, 002, 005, 003, 006 and round again, starting from one picked at random each time the screen opens. Each moves down at 30 pixels a second, at x -170, -300, 211, -32 and 145, from y -791, -1035, -1098, -815 and -1022 to -17, -16, -135, -18 and -25, fading in and out over 2.25 seconds at its ends, with a second of nothing before the next. It draws at 120 of 256 over the room, under the side panel and the frame of bars. The exe reads the sketches as the screen opens, so the order and places are its own; both games share them.

Config's first tab is the same in every game, read from the PC's help lines and measured under Wine on Test Game 92's opening:

- Effects off cuts a timed screen update straight to the new picture, makes a timed image change happen at once, and leaves out named animations and motion blur; the 2.5 second fade-in became a cut while the 4 second wait after it still waited. Flash and screen shake are left out with them, by their names, untested.
- Waits off skips the `[ウエイト]` waits; the opening's fade still played.
- Clicking past waits, when on, lets a click end a `[ウエイト]` wait: a click at 5.5 seconds brought the next picture at 5.8 instead of 6.3.
- Camera work off keeps an event CG whole: timed and immediate image changes don't move or scale a `cg\` picture, though its fades still run, and its named animations don't run. With it on, the opening pans and zooms over the CG.
- Explanations off hides the pop-ups msg_button.ini gives the message window's buttons.
- The second tab's wait time runs from ×0.70 to ×1.30 in steps of 0.01, its bar full at ×2.00, and stretches `[ウエイト]` waits and timed screen updates alike: at ×0.70 the opening's 2.5 second fade took 1.75, and at ×1.30, 3.25.

Config's second tab keeps the rest of the measured options. The confirm key, Space or Enter, is the key that acts as the left button, and the other one acts as the right button, as its help says. "Stop the game when inactive" is off to start. Test Game 92's CG animation switch is byte 76 of `cfg.sav` (1 on, 0 off), and with it off, set and saved by quitting, the first movie scene read the same pictures and movies under Wine; the PC writes `cfg.sav` only when it quits. What it and the manual animation camera switch change is still open.

A scene unlocks once its key script, the last field of its `play_view.ini` line, has been read to its end, measured under Wine on Test Game 89. Leaving its second scene's script partway, after a few lines, and going back to the title left the scene locked, and that script wasn't in `read.sav`. The first scene, whose script `read.sav` lists, was unlocked. A line can name up to three key scripts, with 0 for none, and any one read unlocks the scene: Test Game 84's second scene names two, and the PC unlocked it with a `read.sav` that listed either alone, as well as both. The PC read those files, made by adding names with no ranges read to its own, and unlocked the scenes they named. So the runtime unlocks a scene as one of its scripts ends, and reads `read.sav` to unlock what the PC has. `play_view.sav` isn't about unlocks: unpacked, Test Game 88's has a save's layout, with a date at byte 44004 and sprite records, and the runtime leaves it alone.

When no `cfg.sav` exists the runtime writes the values the PC game wrote on a first run under Wine, listed in each game's table, because a file of zeros sets the PC game's volumes to 0 and turns its confirmations off.

Quick saves are ordinary saves in slots 81 to 88, which the Q-Save page after the ten pages of eight shows. Under Wine a session's first quick save overwrote slot 81 and its second went to slot 82. That a page's eight fill and then wrap is assumed, and so is quick load taking the newest. A card's lock is a global variable, 200 for the first card and on from there: locking Test Game 94's fifth card and then its first, and the first card of Test Game 92, The Alchemist and Yarinaoshi no Christmas, changed only those globals (204, then 200; 200) in the `cfg.sav` the PC wrote as it quit, and nothing while it ran. A locked card shows its closed lock and its Delete disabled, and the next session opened with it locked. Test Games 92 and 94 also draw the card as an empty one on the load screen (`lockdim`); The Alchemist and Christmas draw it as any other. The runtime keeps the lock there in every game, refuses to save over or delete a locked card, and passes it over for a quick save.


Test Game 89's saves come back byte for byte except where the runtime doesn't read yet. Offsets below are from the end of a sprite record's two strings, in 89's layout:
- A sprite running an animation has 1 at offset 388, beside the flag at 387 the runtime reads. The runtime writes 0 there.
- A sprite with no animation has 0 where the runtime writes its slot number, at offset 397, the start of the record's tail. One with an animation has its slot number there in the PC's files too.
- One sprite record holds 200 at offset 527, a value of its own that the runtime doesn't read.
- 13242 and 13246 bytes after the records, the PC writes 6 and 3. 277, 285 and 289 bytes after them, a save made just after a load holds 1, 1 and 10.
- In a save made just after a load, the base record's two alpha fields hold 255 where a fresh one, and the runtime, hold 256.

The runtime writes zeros for the values it doesn't read. A quick save the runtime wrote from the PC's own save loads in the PC game under Wine and shows the same scene. 89's quick saves are slots 61 to 66, after its 60 cards.

A card's comment, typed on the PC's save screen, is the string after the save's first byte: with an input method under Wine, typing あいう on a card of The Alchemist and of Test Game 94 rewrote that save with 6 and the three characters in CP932 at byte 1, and everything after, the flow script's name first, 6 bytes later. With no comment the length is 0 and the flow's name is at 0xCD, the fixed place the runtime had read, so a save with a comment didn't read and showed as an empty card. The runtime reads the comment and shows it on the card in white (`slotcomment`, placed and sized against the PC's: 21 pixels in The Alchemist, 19 in Christmas, 18 in Test Game 94; the last two are MS Gothic, so they were measured under Wine with Ume Gothic, VNDegen's own stand-in for it, put in its place, as Wine had drawn them in another, smaller face), and a card with a save and no comment shows the PC's prompt, クリックでコメントを入力 or Click to set a comment. A click there, on the save or load screen, asks the host for a comment in a text field, and the runtime writes it as the PC does: only the comment changes in the file, the rest as it was. Test Game 94's box stopped at 36 bytes, 36 letters or 18 kana, so a longer comment is cut there, never inside a character. A save VNDegen writes has no comment.


### What a rewritten save keeps

Every PC save the runtime has, 87 of the nine games that play and 79 of the older engine's, is read and written back byte for byte, its size included (`nekosave`, which counts a size difference too). Fields whose meaning isn't known are kept as they were read: each record's fixed part and its last 164 bytes, the block after the records with its list of slots, the tail around the fields the runtime reads, the block before the variables, the 24 bytes after the text on screen, and the two bytes after each sound channel. A save the runtime makes from its own state writes what it knows over the layout's constant bytes; `NEKOSAVE_FRESH=1 nekosave` writes a PC save that way, to show what such a save can't reproduce.

Loading saves on the PC under Wine and saving again at once shows what the PC needs from a save, since what it rebuilds comes out the same either way. A PC save of Test Game 88 made in GOOD Timing, loaded as written and as the runtime writes it from the same state, came back with 22 sprites and with 7: the PC dropped the flipbooks, whose fields above it needs, and played each running animation once and dropped it. A record of a running named animation holds 1 in the byte after `animated` in every PC save; with it set the PC keeps the animation repeating, and without it plays it once, so it says the animation repeats. With both written, the PC's two saves after the load differed only in the time, elapsed frame counts and a few bytes of state that a load sets. The runtime saves a repeating named animation as the PC does, with command 19's own text, its frames since it began and that byte, and a load makes it repeat again. The same check on Test Game 93, from a save whose block after the records held a list of slots, [200], and a timer of 120 before it, and on Test Game 84, from a save whose records' last blocks held a small number at 125, 200 at 130 and floats such as 30.0 after it: in both the PC's save after loading the runtime's version, without any of those, was the same as after loading its own, apart from the time and a sound's position, and on Test Game 93 every frame from 0.6 seconds after the load was the same. So the PC rebuilds or ignores those; the runtime keeps them as read and writes the layout's in its own saves.

A save the runtime made from its own play of Test Game 93, loaded on the PC, lost every picture: that PC names a record's picture twice, and loads it from the second name, which the runtime left empty. It differs by game, and getting it wrong the other way is worse: Test Game 84's PC crashes loading a save with the name twice. The PC's own saves name it twice in the Christmas game, The Alchemist and Test Games 85, 88 and 93, and leave the second empty in Test Games 84, 89, 92 and 94 and the older engine's, which keep their pictures that way (under Wine); the runtime writes each game's way. Test Game 94 was measured with a save the runtime made in its prologue, once each way: with the name once, the PC loaded it at the same line and a quick save there matched the one it made from its own save at that line, picture for picture; with it twice, the PC lost the picture (scale 0.004, alpha 0) and the quick save named a later scene. The PC also writes a scale line with its pivot, `scale_x,1.100000,640,0,2400,linear`, as the runtime now does. After that, a save the runtime made at a node of the prologue and the PC's own save there came back from a load on the PC the same, picture for picture, apart from sound channels the PC keeps for effects that have finished. The PC saves 0, 0 as the anchor of a picture no command gave one, and the runtime now does too.

A splash effect's record (Test Game 88's commands 200 and 201) has no picture of its own. Every record has an empty name 201 bytes into its fixed part, before the engine's extra bytes, and a splash's names its droplet's picture there, followed by command 200's parameters 0, 5, 1 to 4, 6, 10, 11 and 7 to 9, its slot first; other records hold the same block with its defaults (a cap of -1, lives of 500 and 1500, then 30, 10 and 60). Its kind is 25. Matched against the command in the script for all four of Test Game 88's saves with one. The droplets themselves live a second or so and aren't kept; a load brings the emitter back for the scene's next burst, with the speed every one of Test Game 88's emitters has, 300, which the record doesn't hold.

### Table settings for the story-in-exe games' menus

Sets 1 and 2 measured these under Wine on Test Games 82 and 87, and the runtime's tables give them:
- `submenudim hide` leaves them out instead, as Test Game 83's submenus take the main buttons' rows (set 3).
- `submenuopen MS` grows a submenu's buttons from their left edge as it opens, to 1 - (1 - t)^2 of their width, and shrinks them back by (1 - t)^2 as it closes, squeezing their pictures, as Test Game 87's title does over 0.33 s: in a 30 fps recording under Wine, its buttons were 0.19, 0.36, 0.51 ... 0.99 of their width opening and 0.81, 0.64, 0.49 ... 0.04 closing, each within 0.01 of those curves, with the main buttons dimmed and lit at once (set 1).
- `submenudim` on a title dims the main buttons while a submenu is open, to their sheet's last row, and they take no pointer, no help and no press; the button that opened it stays selected, and the right button closes the submenu. A left click elsewhere does nothing.
- `datefield year|month|day|hour|minute X Y [STEP] [blank]`: each part of a card's date at its own place, with nothing between, `blank` leaving out a leading zero (set 2's, for 82; 83 uses it too). `datemark CELL X Y` draws a cell of the date's sheet at its own place on each saved card, as 96's slashes and colon sit (set 2).
- On save cards: `slotpic SHEET X Y` puts a picture on every card, full or empty (87's Save Date); `slotchaptervar SHEET X Y COLS VAR` names the chapter by a scenario variable of the save, a cell of a strip across with rounded edges (87's S 4000); `slotnoseconds` stops a 10-digit sheet's time at the minute; `dateslash2 DX` moves the second slash (2 in 87).
- In Config: `knob NAME SHEET X0 Y STEP`, a knob that sits STEP pixels further on for each unit and that a press or drag on its track moves (87's rose); `hovercols`, the hover help's lines side by side in their sheet (87); a radio's `group`, as a check's, so one Confirmations switch sets all six (87).
- A knob's STEP may have decimals (83's 4.08, a 408-pixel track over 100); `number … blank` leaves out leading zeros and keeps the digits' places (83's volumes); `pic … more A,B,… random` picks one at random each time the screen opens (83's menu room, one of 15).
- `cgflagsbygroup STRIDE` under `screen defaults`: a picture's unlock flag in `cfg.sav` at 48000 + STRIDE × its group (its line's first field) + 4 × its place among its group's lines, in file order, as Test Game 83 keeps them (set 3: 4000, groups 0 to 5, every count matching the ini's lines per group after six endings), in place of 48000 + 4 × its number. `cellcountstep N` spaces the gallery count's digits (83's 15).
- `screen cfgsav` takes `size N`, `tracks AT` and `nostring`: Test Game 83's older `cfg.sav` is 96,000 bytes, its heard tracks are an int each from 92000 in sound_view.ini's order, and nothing moves its flags, where the newer games' file is 104,000 bytes with tracks at 100000 and a string at 44020 whose length moves what follows (set 3).
- With `play_view.ini` empty, `play_view2.ini` lists the scenes, `TAB THUMB BALLOON STEP KEY KEY2 KIND`, by commas in 83 and by tabs in 87: either key read unlocks a scene, and its replay plays the first key's scene alone and comes back (sets 1 and 3, under Wine). `replayflow KEY FLOW` under `screen scene` names a story-table flow instead, for 83's scenes after a choice, which replay the scene before it and the choice. 87's `cg_view.ini` has picture lines by tabs, `PAGE ID PICTURE`, and a header whose fourth field is the scene that replays the entry. `celltotal DIGITS DY STEP` spaces the total's digits (87's 12).
- Test Game 90's `play_view.ini` lines have five fields, `TAB THUMB STEP NUMBER SCRIPT`: the script read unlocks the scene, and its replay plays that script alone and comes back to the Scene screen (set 1, by a file trace under Wine). STEP is -1 on every line and NUMBER counts up by tab; neither changed anything set 1 could see, and the runtime reads neither.
- `replaychapters` under `screen scene`: a `play_view2.ini` line's fourth field is the chapter its card replays, which a game part gives the scenes of, and any of the line's three scripts read unlocks it. Test Game 96's lines are `TAB,THUMB,-1,CHAPTER,SCRIPT,SCRIPT,SCRIPT`; three cards share their scripts and differ in the chapter, and on the PC each opens its own chapter's file and comes back to the Scene screen on the same tab and page (set 2, by a file trace under Wine). Other games keep other numbers in that field (83 and 82 do), so only the table makes it a chapter. A replay whose flow runs off its end, as a chapter's does, goes back to the Scene screen, and so does any replay that reaches a flow's end line: the one-scene replays of Test Games 82, 83, 86, 87, 90 and 96 and 83's three table flows that replay a choice. They had gone to the title, where 83's and 86's PCs come back to the Scene screen on the card's tab (set 3, under Wine). One started from the CG viewer comes back to the viewer at its picture. `replaykeeps` under `screen scene` brings a replay back to the tab and page its card was on, as 96's PC does; other games' screens come back as they open, which no one has measured on their PCs. Starting a replay resets the game's parts and closes a part's open screen, as a new story does: started from a menu over Test Game 90's select screen, a replay had run with the select screen still drawn over it (set 1).
- `layoutpairs` under `screen defaults`: Test Game 96's PC keeps each place's standing picture, and its background, as two records, the slot's own (a dark version) and the slot after it (the picture the script names), the two lightings of its flickering bulb (set 2, from its PC saves). The runtime keeps one picture in the slot itself, so with this key whatever removes or replaces a place's picture clears the slot after it too. Without it a lit picture that a PC save brought stayed on screen after the story removed it. The flicker is drawn from the game's own `cfg\light_info.ini`: ten patterns, `#p N` to `##`, of `light,FRAMES,LEVEL` (the lit picture's strength moves to LEVEL of 255 over that many frames at 60 a second) and `wait,FRAMES`. A pattern plays to its end and another follows. Between the two lightings the runtime draws the dark version and the picture itself over it at the level's strength, as the PC's two records suggest it does. That goes for any `sc\` or `bg\` picture in the scene, blurred ones too, but not a flipbook, a movie or an additive picture, and not a slot whose next slot holds a picture, as the dark record of a loaded PC save's pair does. The dark version is the one numbered 10 higher for a standing picture and 1 higher for a background, when that file exists, is the same size and is at most five eighths as bright (the sum of its colours weighted by its alpha); Config's 背景の電球演出 (the setting `bulb`) turns it off. The brightness rule is the runtime's own, from the game's pictures: a standing picture numbered 010 to 019 has a twin 10 higher at 0.37 to 0.55 of its brightness, the PC's saves pair 016 with 026 and 017 with 027, and backgrounds 001, 002, 003 and 005 have one 1 higher at 0.22 to 0.55, where 000 to 009's neighbour 10 higher is at 0.87 to 0.93 and backgrounds 000, 006, 007, 009 and 010's `_000` is followed by a picture at 0.70 or more that isn't a darker copy (their `_001` has one at 0.18 to 0.55), so those stay still. Set 2 compared one scene with the PC by numbers, the prologue on background 001 with no standing picture, over 88 seconds: the lit frame and the darkest frame are the same on both, and the PC had 18 flickers of 0.13 to 0.54 s, 4.9 s apart on average, where the runtime had 23 of 0.1 to 0.5 s, 3.9 s apart, sampled faster. And one with a standing picture, pose 016 over background 001, over 89 seconds: the lit frame is the same on both and the darkest differs by 0.02 with no pixel over 40, the PC with 18 flickers of up to 0.59 s, 5.0 s apart, and the runtime 22 of up to 0.50 s, 4.0 s apart. Unconfirmed: which pattern follows which (taken at random), what the PC does on the backgrounds and poses that stay still here, and whether the PC lays the lit one over the dark as the runtime does or mixes the two, which differ only at a picture's soft edges and while it fades. There the runtime's way has a step: at full strength it draws the lit picture alone, and from the first level below it the dark one under it, so a half-transparent edge or a half-faded picture covers what is behind it by three quarters where it had covered half. If the PC always draws both records, its edges hold the heavier cover throughout; set 2's lit frame with a standing picture showed no pixel over 40 apart, which is too coarse to tell at an edge. The PC's bulb was off when it ran on a `cfg.sav` the runtime had written and on with its own (set 2), so the runtime's file turns the PC's setting off. Under Wine, in a fresh prefix on a display 1280x1024, the PC opens a 1280x960 window, and its Config offers 1280x960, 1024x768 and 800x600 beside the 16:9 sizes, greying out any taller than the display. In that window the top 720 rows are the 16:9 frame unchanged: the title matches the 16:9 title exactly, and the scene in play matches 16:9's. The square picture is under the bottom 240 rows on every screen, the title included, and the message window's whole layer moves down 240 rows onto it, nothing covering the scene: the same line's text ink lands 240 rows lower at the same x, and so do the click-wait mark and the message buttons, which show with the pointer in their place in the strip. The window picture itself, with its `.alp` (alpha up to 128), lands two rows further, at y 722, measured to the row (median error 0.2 against the picture over the square); where 16:9 puts it couldn't be told to the row, as its alpha has no sharp edge and the scene behind it is unknown.

Whether a frame is 4:3 is Config's `screensize`: 1 to 3 for the 16:9 sizes, 4 to 6 for the 4:3 ones, and 0, automatic and the default, for the shape nearer the host's view, which switches to 4:3 below a width 1.48 times the height and back to 16:9 above 1.60, so a window dragged near the middle doesn't flip. The size within a shape doesn't matter, since the host scales the frame to fit. In Test Game 88's table its six size pictures are radios for `screensize` (`radiooff screensize`: choosing the chosen one again sets 0), never greyed; the setting is kept in VNDegen's own settings file for the game, beside its saves, not in `cfg.sav`. A switch takes effect between frames; the scene, its sprites and the story don't change, and saves don't depend on it, as the 16:9 frame's places are the same in both. Over a game part's open screen with `partplate` the plate and its buttons are drawn in the 16:9 frame, not the strip, so the pointer is taken unshifted there (set 2, on an iPad simulator: Test Game 96's hub drew its plate in the frame and took taps 240 rows lower). What the PC's own 4:3 mode shows on such a screen hasn't been looked at. While a game part's own screen is open the band shows the window's picture without its text, where it had shown the last scene's line under Test Game 90's select screen (set 1, on an iPad simulator). ## Placing and scaling pictures

A sprite's x and y are the top left of the unscaled picture. ## Text placement

The PC engine draws its text from a glyph atlas: Wine's font log (`WINEDEBUG=+font`) shows each game creating its
text font at a cell height and at four times it, with the face init.ini's MsgFont names, and a second font for save
card comments. The official English
releases (The Alchemist, Funbag Fantasy 3 if, Funbag Fantasy 4, Horny Elves and a Moral Orc) ask for Lucida Sans Unicode instead, which
VNDegen maps to Open Sans ([fonts.md](fonts.md)). Text placement was measured by loading the same PC save on the PC
under Wine, with VNDegen's stand-in fonts mapped in place of the Windows ones, and here, and comparing the same lines.
The PC sets each glyph a fixed gap past its own advance and lines a fixed pitch apart, neither of which init.ini's
MsgCharInterval and MsgLineInterval predict, so each game's table gives them (`textgap`, `textline`, `textshift`,
`textfont`, `textsize`, and for the log `rows` with a size, `loggap` and `logline`). Some games create their text
font smaller than init.ini's MsgFontSize says, which Wine's font log shows: Test Games 92 and 93 at 22 for 25, Test
Game 94 at 21 for 24. A size fitted only by where lines end can't show this, since a gap makes up the width, so each
was checked by the glyphs' height against the PC's capture too. Test Game 94: size 21, gap 2, lines 28 apart, the
first glyph 2 pixels in and the baseline 1 higher. Test Game 88: gap 2, lines 27, 2 in, 1 higher. Test Game 92 and
Ore o Hoshigaru Tsuma to Gibo: size 22, gap 2, lines 29, 2 in. Each log was placed under its rules as the PC's is,
and the fitted lines end on the PC's pixel or one off. Yarinaoshi no Christmas asks for Meiryo at a 32-pixel cell, which Windows draws at about 21 pixels
to the em, two thirds of the cell; Ume P Gothic, its stand-in, fills the cell, so under Wine the PC's lines run off

## The CG viewer

The panel's art, its buttons' places and their help lines were matched against screenshots of The Alchemist, Yarinaoshi no Christmas, Funbag Fantasy 4, Ore o Hoshigaru Tsuma to Gibo and Horny Elves and a Moral Orc under Wine, and the panel, buttons and picture match the PC's to within blending noise. The PC games behave alike:
- The zoom runs from 1.00 to 3.00 in steps of 0.05, from the buttons or a wheel notch, and keeps the point under the pointer still. Zoom out and reset are disabled at 1.00, and zoom in at 3.00. Reset is immediate.
- The slideshow moves on every 8 seconds.
- The entry's music, the fourth field of its line in `cg_view.ini`, starts with the viewer at the music screen's volume. Its button mutes and unmutes it while it goes on playing.
- A right click hides or shows the panel, and a click on the picture does nothing.
- Previous lands on an entry's last picture when it crosses into another gallery tab or wraps round, and otherwise on its first. Next always lands on the first.
- A disabled button shows no help. The variant buttons are disabled for an entry of one picture, as Funbag Fantasy 4 shows, and not for an entry with only one of several pictures unlocked.
- The Alchemist's art button switches the same setting as Config's Change Illustration and the message window's art button.

Ore o Hoshigaru Tsuma to Gibo's `cfg\change_texture_list.ini` lists each CG group with two flags instead of Haha Sannin to Ana Asobi's pairs of pictures: whether the group has a version with the protagonist see-through and one without pubic hair. The third number of a CG's name picks the version, 100 for the first, 1 for the second and 101 for both, so `cg_000_000_100_000_000.bmp` is `cg_000_000_000_000_000.bmp` with the protagonist see-through. Its CG viewer has a play and a mute button in place of one music button, and switches for the two versions, which change the picture at once and are the same settings as Config's. Their help lines are Config's, in `h004_004.bmp`. Its message window's picture reaches 721 pixels down, and the PC's screen stays 720.

Horny Elves and a Moral Orc's `cg_view.ini` header has no type field, so its BGM comes third, and each picture line names its replay flow fourth. Its viewer's help comes up as speech bubbles, which fade in.

Slider fills round to the nearest pixel: at 60, The Alchemist's 173-pixel music bar fills 104 and Yarinaoshi no Christmas's 161-pixel one 97.

## Games with their story in the exe

Test Games 82, 83, 86, 87, 90 and 96 have no flow scripts: the order of their scenes, choices and route variables is in the exe. The order is found black-box, by tracing which scene scripts the PC game opens under Wine, in order, through each route, and written as data in the game's table, under `screen story` (the format is at the top of `core/story.cpp`, and `core/tables/storytest.inc` is an example). Each `flow` there compiles to the nodes a flow script has, so the same flow interpreter runs it. A PC save of these games names no flow, only the scene and its node (checked in a save of Test Game 82), so the runtime's saves of them name none either. VNDegen's own file beside its save keeps the exact place in the story, the last choice's or screen's result, and a game part's screen left open. That place is a line of the table as it was when the save was made, so the file also keeps a number made from the table's lines (`storytable`): when a later version's table differs, the place isn't used and the save resumes as a PC save does, with the file's result still taken. The number leaves out a line's trailing comment. The save's flow node is the PC's number for the line only when the table gives one, and a compiled node's own number otherwise, so the file also says which it is (`storynumber`), and a node that is no PC number isn't looked up as one: the save goes on from its scene's line. A file from before `storynumber` was kept gets the line when the save is made again: the node counts as a PC number when a line of the scripts the place is in has that number and is the save's scene or a line that isn't a scene. That can miss a number held from a chapter the story has left, and the save then goes on from its scene's line as above. A file from before `storytable` was kept is trusted as it is: its place is used whatever the table. A PC save, without that, goes on after the first `scene` line that names the save's scene, or inside a chapter that plays it, with the game parts' state loaded first, since a chapter's scenes can depend on it.

Their PC saves hold the exe's own number for the place in the story as the flow node, 10 to an entry within a chapter in Test Game 87, and the PC needs it: a save of VNDegen's with another number loads on the PC but goes black at the scene's end, and the same save with the PC's number goes on (set 1, under Wine). It also names the chapter on the save's card. A table line can carry it as `@N`, which the runtime writes and a PC save is resumed from before the scene's name. While a choice waits a save holds 3 where it holds 1 in a scene, the choice's own number, and 2 where the last choice's result goes, 112 bytes into the block before the variables; Test Game 83 holds 2 there in scenes too from the first choice on, whichever option was taken (set 3, from saves after each option of the same choice), which `lastchoice made` gives. Numbers repeat: in Test Game 87 both options of a choice share one, a chapter's last scene carries the next chapter's base, and each ending's last scene is 9999 (set 1, from 67 PC saves), so a load takes the line with the save's number whose scene the save names, and the first with the number when none names it. The PC doesn't save during a staff roll, and nor does the runtime.

Test Game 82 keeps all sixteen of its options in one sheet, a column each with the usual five rows, and each choice shows some of its columns: a table line gives them as `cells`, and `choicecolumns 16` under `screen choice` divides the sheet. Its box shows the chosen option pressed, in row 2, then shrinks about its middle and fades out in about 0.28 seconds before the story goes on (`close 280 0.42`), timed from Wine shots' file times by set 2 and so approximate.

What one of these games does that no other does, such as Test Game 90's face pictures and select screens or Test Game 96's comments, is a game part: a file of its own under `core/` that the list in `core/parts.cpp` names and the game's table turns on with `parts NAME` under `screen defaults` (`core/parts.h`). A part takes the scene commands the engine doesn't know, draws at fixed layers of the frame, opens screens the story table's `open` line waits on and branches on, gives a chapter's scenes, and keeps its own state with a save, in the PC's save and in VNDegen's file beside it.
