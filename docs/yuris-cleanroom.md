# YU-RIS runtime: clean-room provenance

VNDegen's YU-RIS runtime (`Packages/VNDegenKit/Sources/CYuRIS`, the `EngineYuRIS` plugin and the Linux host in
`Engines/YuRIS/host`) is VNDegen's own code under the MIT license. No other runtime for YU-RIS exists. It was written
without reading the code of any GPL, LGPL or unlicensed YU-RIS tool, such as yuri, YurisKeyFinder (GPL-3.0),
YPF-Manager, RxYuris or yu-ris-ext-ybn. This file lists where each part's knowledge came from.

## How each part was built

- **Archives.** Layout from GARbro's `ArcYPF.cs`; the name length is chosen by matching the stored hash rather than
  by GARbro's swap tables (see below), and the entry tail width by the directory size.
- **Script files.** Container layouts from YuRISTools (`YSCM.cs`, `YSTB.cs`, `YSER.cs`). The XOR sections restart
  the key per section, as GARbro's `DecryptYstb` does. `ysv.ybn`, `ysl.ybn`, `yst_list.ybn` and `yscfg.ybn` were read
  from the game files: entry layouts were fitted until every file of the 5 games parsed to its exact end. String
  initial values in `ysv.ybn` are expressions, which the runtime evaluates in id order at start.
- **Expressions and assignments.** Token opcodes were read from probe scripts compiled with the SDK compiler (the SDK
  engine run under Wine in release mode writes `data/ysbin`): `<` `S` (<=) `>` `Z` (>=) `=` `!`, `&` and `|`
  logical, `A` `O` `^` bitwise (the manual says & | ^ are bitwise in source), `R` negate, `s` and `i` conversions, and
  the compound assignment operator in the high byte of an argument's type (1 +=, 2 -=, 3 *=, 4 /=, 5 %=). String
  literals may be quoted with `"`, `'` or a backquote, seen in the games' own arguments.
- **System variables.** Ids differ between engine versions. `sysvar_tables.c` was generated by compiling a probe that
  reads every system variable named in the manual with the 0.466, 0.479 and 0.495 SDK compilers and reading the ids
  from the output. Each game's version was matched to a table by comparing the type and dimensions of its 1000 system
  entries in `ysv.ybn` with the SDK-compiled ones: 466 matches 0.466, 474 matches 0.479, 481 and 555 match 0.495
  exactly. 488 (Saimin Seishidou) matches none and still needs its own table.
- **Start.** The 0.495 engine refuses to start without the label `SYSTEM_START` (its error dialog under Wine), so the
  runtime starts there, else at the top of `system_start.yst`.
- **Text output.** Probe scripts run under the 0.495 engine with a second task sampling `$_TEXT_FLAG` every frame:
  WORD and `_` append without resting, with flag `2` per full-width and `1` per half-width character; RETURNCODE adds
  `E` and rests; both variables are empty once the task runs on. ERIS's `\r`, `\p` and `\c` print the two-byte codes
  0xEFF0, 0xEFF2 and 0xEFF3 (ERIS `macro.yst`).
- **Commands.** Keyword meanings come from the SDK manual (0.479 and 0.495 HTML). Undocumented CG keywords (FX, FBX,
  FCX, FRZ, F and others) were read from how ERIS's camera code sets them; LINT and BNO likewise.

## Open questions and how they were settled

- **Archive name lengths.** The `.ypf` name length byte is scrambled with a swap table that differs between games:
  Saimin Gakushū uses a table GARbro doesn't list. The runtime doesn't use a table. It takes each entry's length from
  the candidate whose decrypted name matches the entry's stored MurmurHash2, which was confirmed on every archive of
  the 5 test games.
- **Archive entry tail.** After the name, type, flags and sizes, an entry has a 4- or 8-byte offset and a 4-byte
  checksum. The width doesn't follow the archive version (MA☆KO HUNTER's version 500 archives have 4-byte offsets,
  Saimin Gakushū's version 500 archives 8-byte ones), so the runtime picks the width whose entries end exactly at the
  directory size in the header.
- **Script key.** The XOR key differs per game (`0x96AC6FD3` in two games, three others each have their own). The
  first argument entry's data offset is always 0, so its encrypted offset field is the key.
