# ArchiveImport

Turns a zip, RAR, 7z, or ISO archive, or a GOG installer, into a game folder in Games. `ArchiveImportView` is the whole flow. `ArchiveImporter` is its state machine, and `ArchiveDropTarget` is a drop area the hub can place.

## Extraction library

Extraction uses the libarchive that ships with iOS and macOS. Both SDKs include `libarchive.tbd` but no headers, so `CArchive/include/CArchive.h` declares the calls this module makes, following libarchive 3.7's `archive.h`. libarchive is BSD-2-Clause and adds nothing to the app's size.

It was chosen by testing on archives from the user's library (2026-10-25). The system libarchive on macOS (3.7.4, built with zlib, liblzma, and bzip2) extracted all of these. The iOS 27 simulator extracted all but the zip64 and split 7z ones, which were tested on macOS only:

| Archive | Format | Result |
|---|---|---|
| Test Game 01 (516 MB) | zip, Deflate, 2,668 code page 932 names without the UTF-8 flag | 2,635 files, names decoded |
| Test Game 02 (155 MB) | RAR5 | 609 files |
| Test Game 03 (188 MB) | RAR4 | 641 files |
| Test Game 04 (145 MB) | 7z, LZMA2 + LZMA + BCJ2, solid | 1,596 files |
| Test Game 05 (1.4 GB) | RAR4, 29 old-style volumes (`.rar`, `.r00` to `.r27`) | 1 file, CRC matches |
| Two scene RARs | RAR4 holding another RAR | nested import |
| Synthetic | zip64 (4.6 GB entry), split `.7z.001`, AES-256 and ZipCrypto zips | extracted |

Two gaps showed up, and none of the 516 archives in the user's library hits either. A header scan of all 149 zips found only Store and Deflate, and no RAR or 7z there has encrypted headers or an encrypted first file.

- **Deflate64.** libarchive reports "Unsupported ZIP compression method (9)". Windows writes Deflate64 when it zips large files, so `Deflate64.swift` reads those entries straight from the zip with zlib's `contrib/infback9` (zlib license, vendored unmodified in `CArchive/`, see `LICENSE-zlib.txt`).
- **RAR and 7z encryption.** libarchive decrypts zip only. Encrypted RAR or 7z archives get a message saying so. Supporting them would mean adding UnRAR (freeware license that forbids writing RAR) and 7-Zip's AES code.

No other candidate covers everything either. SWCompression decodes in memory, which rules out multi-GB archives, and has no RAR. ZIPFoundation is zip only and has no Deflate64. UnrarKit is RAR only.

## Behavior

- **Names.** A name that is valid UTF-8 stays UTF-8. Anything else is decoded as code page 932, the Windows superset of Shift-JIS, then Windows-1252. Path parts `.` and `..` are dropped, so an entry can't escape the game folder.
- **Layout.** When the archive holds one top-level folder, that folder's contents become the game folder. `__MACOSX` and `.DS_Store` don't count.
- **Choosing.** iOS and macOS use SwiftUI's `.fileImporter`, which the system presents modally. iOS 27 simulators also worked with the embedded `UIDocumentPickerViewController` it replaced, but on an iPhone its Open button did nothing (user report, 0.1.1). The picker, drops, and the importer log to the `archiveimport` category of `com.chronostriker1.vndegen` with file names and whether security-scoped access was granted.
- **Drops.** `onArchiveDrop` takes Finder drops as file URLs. On iPhone and iPad a drop from Files holds item providers, which are opened in place when the source allows it. Otherwise the system's copy is copied under file coordination into `tmp/Dropped Archives/<UUID>`. The library and the import sheet both accept drops.
- **Open in VNDegen.** The app declares zip, RAR, and 7z as documents it can view, at `Alternate` rank, so Share and Open With in Files and Finder list it. Open With in Files opens the archive in place. Other apps, and `simctl openurl` on the simulator, deliver a copy into `Documents/Inbox`. An import sheet already showing takes the archive, unless an extraction is running.
- **Copies.** A drop copy or an Inbox copy belongs to the importer that takes it. The importer deletes it when the flow ends or a newer choice replaces it, and never offers "Delete archive after import" for it. Copies that arrive while an extraction runs, after the flow ended, or while another sheet is showing are deleted at once (`ArchiveImporter.discard`). Copies left by a process that was killed mid-flow go later. Drop copies are deleted at launch (`discardStaleDropCopies`). Inbox copies are deleted when the app goes to the background (`discardInboxCopies(addedBefore:)`), and only a copy that no choice still holds and that was already in the Inbox when the app last went to the background. A choice holds its files until its last listing or extraction finishes, even after its sheet closed. The age rule protects a copy on its way to an import sheet: opening an archive in VNDegen from another app writes its Inbox copy before the URL callback runs, and at a cold launch before the app launches. Deleting the Inbox at launch removed that copy before the sheet took it (simulator, cold launch through `simctl openurl`). A copy whose added date can't be read is kept.
- **Coordination.** Listing and extraction read every volume inside a coordinated read (`NSFileCoordinator`), using the URLs the coordinator hands out, so a file provider such as iCloud Drive can't move, replace, or evict the archive mid-read. A coordinated read also waits for an evicted file to download.
- **Overlapping choices.** Each choice owns its security-scoped access and copies until its own listing or extraction finishes. A choice made while an earlier one is still listing or extracting replaces it on screen at once, and the earlier one's late result is dropped.
- **Volumes.** Picking any part of `name.partN.rar`, `name.rar` with `name.r00`, or `name.7z.001` pulls in the other parts when their folder can be listed. Outside the app's container on iOS, the picker grants access only to the picked files, so the user selects every part (inferred from the sandbox rules, not tested). Missing parts are reported by number, and so are two files that are the same part, such as `name.part1.rar` and `name.part01.rar`. Split parts keep their format, so `name.zip.001` and `name.7z.001` are two archives. No `.partN.rar` set exists in the user's library, so that naming is covered by unit tests only.
- **Staging.** Files are extracted into `Games/.importing/<UUID>` and moved into Games only when everything succeeded. A failure or cancel deletes the staging folder. The library scan skips dot folders, and a new `ArchiveImporter` deletes staging folders left by a crash.
- **Nested archives.** When the result has no subfolders and holds one archive (or one volume set) next to loose files such as a readme, the user can extract that too. The same goes for a result that holds only one folder with such an archive in it. An installer's own result never gets the prompt: a GOG game with no subfolders, such as a Godot game's `.exe` and `.pck`, keeps GOG's `webcache.zip` beside them, which isn't a wrapper. Accepting keeps only the inner archive's contents.
- **Space and progress.** A listing pass reads headers only and seeks past file data. On the Mac mini it took 0.3 s or less per test archive once cached, and 3.2 s for one uncached 145 MB zip. It gives the exact byte and file totals for the free-space check and the progress bar. Each file and folder also counts 4 KB, so an archive of many empty files can't fill the device. The import starts only when that total plus a 100 MB reserve is free.
- **Limits.** Header sizes are untrusted. A negative size, or a total over 1 PiB, rejects the archive before anything is written. While extracting, the import stops when the files use more than the listing promised, which is what a decompression bomb or an archive changed after listing does, and when free space falls below the 100 MB reserve. Free space is checked every 64 MB written or every quarter second. Deflate64 entries stop at their listed size while they decompress.
- **Ready to import.** `LocalArchives.find` lists the archives at the top level of the Games folder, and on iPhone and iPad also of `Documents`, which Files shows as VNDegen. Each volume set is listed once, under its first volume, and only when that first volume is there. Folders, dot files, and the Inbox are skipped. The hub lists them on the empty library and the library home and passes the first volume to the import sheet, which reads it in place with no security scope. A sideloaded iPhone install whose picker, drops, and Open in VNDegen all failed (the system logged `Could not resolve bookmark`, Cocoa error 257, and an empty `didPickDocumentURLs`) could still read and write its own container, which is why this path exists (user report, 0.1.2).
- **Deleting the archive.** "Delete archive after import" is offered only for an archive inside VNDegen's own folders: the app's container on iOS, or the Games folder on the Mac. Anywhere else the file may be synced by iCloud Drive, Dropbox, OneDrive, or a server, and deleting it would delete it on the user's other devices too. It starts on for an archive the library lists under Ready to import, which the user copied in only to import it. Each volume's file number, size, and modification date are recorded when it is listed. After the import, each volume is deleted inside a coordinated write only when the file at its path still matches. A volume replaced or changed meanwhile, such as one copied over in Files while the nested archive prompt showed, stays, and the result says so.

## Installers

A picked `.exe`, or `-N.bin`, makes `ArchiveSource` an installer source. Its volumes are each setup's `.exe` followed by its `.bin` parts. Picking one `.exe` also takes the `.bin` parts beside it and the other `.exe` files whose GOG build number, the `(nnnnn)` before `.exe`, is the same, when the folder can be listed. The listing pass opens each setup with `RuntimePackages`' `GameInstaller`, which reads the Inno Setup 5 headers and the game's `goggame-<id>.info`. A GOG add-on is a setup whose `rootGameId` differs from its `gameId`. It joins the main setup whose `gameId` is that root, and `includeAddOns` (on by default) decides whether it is unpacked after the main game into the same folder. A picked add-on without its main setup is refused, and so is a pick of two main setups. A sibling setup that doesn't open or belongs to another game is ignored. Its files stay out of "Delete installer after import", which deletes only the volumes of the setups that were unpacked.

The space check and the extraction limits work as for archives, with sizes from the installer's headers: the files of the setups that will be unpacked plus 4 KB for each file and folder. Extraction writes through `FileCase.resolve`, so an add-on's `data\patch.xp3` lands in the main game's `Data` folder. An archive whose only content is an installer gets the nested prompt, worded for installers, and the installer is unpacked from the staging folder. The folder name becomes the installer's title unless the user changed the archive's suggested name first.

`GameInstaller` keeps only `{app}` files and GOG Galaxy files, and leaves out `{tmp}`, `{commonappdata}`, `__redist`, the uninstaller, and files whose GOG check names another language or a 32-bit build only. It refuses setups that unpack their data with ISDone or unarc (repacked installers), encrypted setups, Inno Setup 6 and other versions outside 5.x, and executables that aren't Inno Setup. It was compared file for file with innoextract 1.9 on the library's GOG installers: Revenge of the Orcs with its unrated add-on, Forbidden Ward (`-1.bin`), Two Beasts Or Not To Beast! (20,973 files), Sacrifice Villains unrated (`-1.bin` and `-2.bin`, 6.9 GB), and La-Mulana (LZMA2, an older GOG layout).

ISO 9660 images, with Joliet names, are read by the system libarchive like any other archive. A BIN/CUE image goes through the same reader: `CueSheet` reads the cue's first data track (MODE1/2352, MODE2/2352, MODE2/2336 or MODE1/2048), and `CArchive/raw_sectors.c` hands libarchive each sector's 2048 bytes of data through its read, skip and seek callbacks. When a disc's top level holds `autorun.inf`, only setup or autorun programs, and one folder with a program in it, `ArchiveExtractor.gameRoot` takes that folder as the game. `disc.bin` and `disc.cue` in the test fixtures are such a CD, made by `make-fixtures.sh` with `hdiutil`.

## Games packed into one .exe

Some RPG Maker MV games ship as one Enigma Virtual Box `.exe`: NW.js's own `Game.exe` with the game's whole folder appended in two extra PE sections. `EnigmaPack` reads that folder without running anything. The layout was worked out from the library's three such games and checked against the format notes of evbunpack (Apache-2.0, read only, no code taken):

- The section named `.enigma1` holds, within its first 4 KB, a 64-byte header: `EVB\0`, a 32-bit header size of 64, a layout number at offset 20, and at offset 48 the pack's total size counted from the header. Layout 3 (2019 to 2024 builds) keeps a file table and then every file's data in table order. Layout 1 (2017) puts each file's data right after its record.
- A main record follows the header: the table size (layout 3) and the number of top-level folders. Each record is a 16-byte head (a size used by layout 1, an id, a parent id, a child count), a UTF-16 name ending in two zero bytes, and a type: 3 for a folder, 2 for a file. A layout 3 folder has 25 more bytes and a file 53, with its size at offset 2 and its stored size at offset 49. A layout 1 record ends with a 49-byte block holding the size at offset 2 and the stored size at offset 41. Folders list their children depth first.
- `%DEFAULT FOLDER%` is the folder beside the `.exe`. Other top-level folders stand for Windows folders and are skipped.
- A file whose stored size differs from its size is compressed (aPLib, in Enigma's own chunking). None of the library's games compress, so such packs are refused.

A pack is accepted only when its records add up to the total its header gives, so a variant this reader doesn't know is refused rather than unpacked wrong. All three library games (two layout 3, one layout 1) and evbunpack's ten test packs (2017 to 2024, x86 and x64) read this way, and the unpacked files matched a separate scratch reader byte for byte.

When a pack holds NW.js (`nw.pak`), the files `DesktopRuntimeFiles.nwjs` lists are left out, the same ones Remove engine files would offer. A picked `.exe` that is a pack is listed this way instead of as an installer. An archive whose extraction holds exactly one `.exe` at its top that is a pack gets the nested prompt, and so does one whose top holds only a folder with such an `.exe`, as in `GAME-RJ206092/たままお一転後ver1.00/tamamao15.exe`. Accepting unpacks the game into that same folder, beside the archive's readme and `www/save`, and deletes the `.exe`.

## NW.js packages

NW.js runs a game whose web files are zipped into `package.nw` beside its `.exe`, and WebKit can't read a zip. After an archive or installer is extracted, and when there is no nested prompt, `ArchiveExtractor.unpackPackageNW` looks at the game folder. When it holds `nw.dll` or `nw.pak` and a `package.nw` file, the zip is listed, checked against free space as an archive is, and extracted into a dot folder beside it under the same limits. Only when that holds an `index.html` does it replace the file, under the same name, since NW.js runs a `package.nw` folder as well. Otherwise the dot folder goes and the file stays. Dungeon Vixens (Construct 3, GOG) is the library's game this is for. A failure here fails the import as an extraction failure would.

## Electron installers

electron-builder's NSIS installer stores the app as `$PLUGINSDIR/app-64.7z`, uncompressed, right after a small PE stub, so the 7z sits in the `.exe` byte for byte. `NSISPayload.offset` finds it without running anything: the PE overlay starts where the last section's raw data ends, NSIS's 28-byte first header sits there (`0xDEADBEEF`, `NullsoftInst`, and the length of everything from that header on), and then come blocks, each a 32-bit length whose high bit marks it compressed. The first stored block that starts with the 7z signature is the payload. libarchive 3.8 finds such a 7z on its own, but the 3.7.4 in macOS and iOS starts its self-extractor scan at 0x27000, and The Titjob Apparition of the Midnight School's starts at 0x25B5D, so `CArchive/window.c` hands libarchive the file from that offset through its read, skip and seek callbacks. A solid NSIS installer, which hides the 7z inside its compression, isn't covered.

A picked `.exe` with such a payload is listed and extracted like an archive. An archive whose extraction holds one such `.exe` gets the nested prompt for a game packed into one `.exe`, and accepting unpacks the app into the same folder and deletes the `.exe`.

After that, as for `package.nw`, `ArchiveExtractor.unpackAppAsar` unpacks `resources/app.asar` into `resources/app`, which Electron loads when there is no `app.asar`, and deletes the archive and any `app.asar.unpacked`. It does so only when the asar holds `js/rmmz_core.js` or `js/rpg_core.js`, since VNDegen runs RPG Maker MV and MZ games from folders, while TyranoScript and Visual Novel Maker games run from the asar as they are. `AsarArchive` skips entries whose size is not a whole number or whose bytes would lie outside the file, and entries named `.`, `..` or nothing, instead of refusing the whole archive: Titjob's index has ten entries of 1 GiB at offset 0 and eight whose sizes are around 1e307, put there to stop unpackers, and nothing ever reads them.

## RPG Maker VX Ace self-extractors

RPG Maker VX Ace's "compress game data" writes the game as a cabinet appended to an 85 KB extractor that reads the RTP's place from `Software\Enterbrain\RPGVX2`. libarchive's CAB support isn't enabled, its self-extractor scan covers only the first 128 KiB, and its LZX decoder fails on Succubus Hunt!'s cabinet inside the encrypted `Game.rgss3a` (an uncompressed LZX block whose pad byte falls in the next CFDATA), on macOS's 3.7.4 as on 3.8.5. VNDegen doesn't write its own LZX reader. `RPGMakerCabinet.isPacked` recognizes the extractor instead: a PE whose overlay starts with `MSCF`, whose cabinet runs to the end of the file, and whose stub names that registry key. A picked `.exe` like that is refused while it is listed, and an archive whose extraction holds one, at its top or in its only folder, stops before the game is added, both with `ArchiveError.compressedRPGMakerGame`, which tells the player to extract it on a PC or with 7-Zip.
